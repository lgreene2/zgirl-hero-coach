# Z-Girl v3.11 — Operational Activation Runbook

## Purpose

Move a real qualified institution from GLS opportunity through a governed Z-Girl pilot, evidence closeout, renewal and expansion without creating a duplicate CRM or weakening participant privacy.

## System-of-record boundary

**GLS owns:** institutional prospect/opportunity, proposal, agreement, invoice/payment state, recognized commercial value, relationship-stage next action.

**Z-Girl owns:** institution implementation profile, pilot readiness, operational roles, cohort configuration, launch milestones, aggregate adoption/activity, implementation evidence, permissions, closeout, facilitator-learning signals, renewal/expansion implementation recommendations.

No participant private-reflection text crosses this boundary.

## Real activation order

1. Confirm v3.11 production health and database security.
2. Establish the first real named global System Owner through the existing Identity & Access bootstrap pathway.
3. Select a qualified GLS institutional opportunity using the first-pilot scorecard.
4. Create the Z-Girl Institution Record only when the institution is legitimately entering implementation preparation.
5. Assign the appropriate institution-scoped Institutional Admin; do not grant broader global roles for convenience.
6. Create the pilot from the GLS opportunity handoff.
7. Complete the eight qualification gates.
8. Confirm agreement/scope boundary in GLS.
9. Confirm named System Owner and implementation contact.
10. Complete the full 12-item readiness set, facilitator assignment, safety contact and at least one ready cohort.
11. Move to Pilot Ready.
12. For commercial pilots, require executed-agreement authority from GLS before Live. Public checkout/payment completion is not required to launch an invoice-based institutional engagement.
13. Activate the cohort(s) using the approved profile(s).
14. Record aggregate implementation analytics and provenance-labeled evidence only.
15. Conduct midpoint implementation review and capture friction/support/accessibility issues.
16. Move to Evidence Collection only after implementation evidence exists.
17. Prepare closeout draft and renewal/expansion recommendations.
18. Complete the pilot only after evidence plus closeout draft exist.
19. Finalize the evidence package only in Completed/Renewal/Expansion status.
20. Synchronize implementation status to GLS for renewal/expansion opportunity management.

## Operational stage gates

**Opportunity → Qualified** requires accessible decision maker, defined manageable group, structured-feedback commitment, credible use case, realistic access, confirmed safety route, and confirmed privacy requirements.

**Qualified → Agreement/Scope** requires a GLS opportunity for commercial work.

**Agreement/Scope → Institution Setup** requires a real active named global System Owner.

**Institution Setup → Onboarding** requires an active Institutional Admin or Implementation Contact assignment.

**Onboarding → Pilot Ready** requires all 12 readiness gates, a ready/active cohort, active facilitator, and active safety contact.

**Pilot Ready → Live** requires the appropriate engagement authority. A commercial pilot must have executed-agreement authority or a later invoice/payment administrative status. Paid public checkout is not a prerequisite.

**Live → Evidence Collection** requires at least one aggregate metric or evidence record.

**Evidence Collection → Completed** requires at least one provenance-labeled evidence record and a substantive implementation closeout draft.

**Completed → Renewal / Expansion** feeds the GLS relationship lifecycle.

## Participant/cohort boundary

The institutional admin layer uses aggregate cohort structures and counts. It does not require an individual participant registry and must not store private reflection text, journals, diagnosis/treatment data, counseling notes, safeguarding narratives, clinical records, clergy/spiritual-direction records, sports-medicine data, or payment-card data.

## Evidence rules

Every evidence record identifies its claim type and provenance. Observed, system analytic, administrator-reported, facilitator-reported, and participant-reported evidence are never silently blended.

Participant feedback in institutional evidence must be aggregate or otherwise governed by the approved implementation/permission process.

## Test records

Governed QA records must use `is_test=true`. Test rows may prove workflows but may never be represented as production implementation evidence, testimonials, case studies, institutional references, or commercial proof.

## First real pilot closeout

At closeout produce:

- implementation summary
- executive outcome brief
- aggregate implementation scorecard
- evidence provenance register
- facilitator-learning signals
- permission status record
- renewal recommendation
- expansion recommendation
- case-study readiness decision

Then route commercial follow-up back to GLS.
